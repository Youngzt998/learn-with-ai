Every tensor one MoE layer touches in a forward pass, and the interface of every kernel that reads or writes it. One square is one element, drawn to scale with toy sizes: T = 6 tokens, hidden size H = 8, E = 4 experts, top-k = 2, expert width I = 5. What real implementations change (not drawn)

  1. Fusion. Production kernels merge most of these launches. In vLLM's Triton path (2025), softmax and top-k (launches 2–3) are one topk_softmax kernel, and launches 5–7 collapse into moe_align_block_size. The permuted buffers are never written: both grouped GEMMs read and write rows in (token, slot) order and use the sorted index list only to decide which rows each tile works on. GEMM 2 also multiplies by the routing weight, and a small moe_sum adds the k slots.
  2. Padding and a tile-to-expert table. Grouped GEMM kernels want each expert's segment padded to a multiple of the tile height, plus an expert id per tile or per row, so a CTA knows which weight slice to load without searching expert_offsets (vLLM's expert_ids, DeepGEMM's contiguous layout).
  3. Decode under CUDA graphs. The CPU does not know tokens_per_expert in advance, so masked layouts use a fixed [E, max_m, H] buffer plus a count of valid rows per expert (DeepGEMM's masked layout).
  4. Expert parallelism across GPUs. Experts live on different GPUs. Launch 8 becomes a dispatch and launch 12 a combine: all-to-all exchanges between GPUs, which libraries such as DeepEP implement.
  5. Shared experts. DeepSeek-V2/V3 and Qwen2-MoE add a dense FFN that every token goes through; its output is added to Y.
  6. Router variants. DeepSeek-V3 scores experts with a sigmoid, adds a per-expert bias only when choosing them (auxiliary-loss-free load balancing), limits each token to the best expert groups, then normalizes the chosen scores and scales them by routed_scaling_factor.
  7. Low precision. With FP8, every GEMM interface gains scale tensors; DeepSeek-V3 keeps one scale per 1×128 activation tile and one per 128×128 weight block.
  8. The other extreme. In 2026 DeepGEMM added a fused Mega MoE kernel that overlaps NVLink communication with the expert computation.

Scope: one MoE layer, forward pass, one GPU. dtypes are typical for BF16 inference (bf16 stands for __nv_bfloat16); many implementations keep router math in FP32. Weights are drawn as [in, out] so the math reads X · W; checkpoints usually store the nn.Linear layout [out, in], and kernels read it transposed.

Illustrative, not measured: the routing probabilities are made up. Rows inside an expert are drawn in token order, which a stable ranking in launch 7 produces; ranking with atomicAdd gives some other order and the same final Y. Launch 5 also needs tokens_per_expert zeroed first, a memset that is not drawn.
